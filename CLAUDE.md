# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão Geral

Sistema web de fluxo de caixa para prefeituras, estados e órgãos públicos. Backend em **FastAPI + SQLAlchemy 2.0**, templates **Jinja2** server-rendered (não é SPA), banco padrão **SQLite** em `instance/fluxo.db` (PostgreSQL suportado via `DATABASE_URL`). Inclui motor de simulação de cenários (regressão, média histórica, modelos econométricos com XGBoost/LightGBM/statsmodels) para projeção de receitas e despesas públicas.

### Banco de dados
- **Schema gerenciado por Alembic** (`alembic/` na raiz). Toda mudança de schema = revisão com upgrade/downgrade: `alembic revision --autogenerate -m "descricao"` após alterar models. Nunca use `create_all` para tabelas de negócio.
- Boot (`create_app`): `preparar_banco()` (`bootstrap_db.py`) roda `alembic upgrade head` se `AUTO_MIGRATE` (default true); depois `seed_dominio()` (sempre, idempotente e não destrutivo) e `seed_data()` se `SEED_DEMO_DATA` (default true).
- **Banco legado** (criado antes do Alembic, sem `alembic_version`): boot aborta pedindo `alembic stamp 0001` (marca a baseline; o boot aplica as migrações posteriores). NUNCA `stamp head` na adoção — marcaria migrações não executadas como aplicadas.
- Teste anti-deriva: `src/tests/integration/test_migracoes.py::test_sem_deriva_entre_models_e_migracoes` falha se um model mudar sem migração correspondente.
- Naming convention de constraints em `models/base.py` (`NAMING_CONVENTION`) — obrigatória para o batch mode do SQLite; não criar constraints com nomes fora do padrão.
- **Índices e sargabilidade** (change `indices-e-filtros-sargaveis`, R12): `flc_lancamento` tem índices `(ind_status, dat_lancamento)`, `(seq_qualificador, dat_lancamento)`, `(seq_conta, dat_lancamento)` e `(seq_etl_staging)` — migração `0032` + `__table_args__` no model (anti-deriva). ⚠️ **Filtro de período é FAIXA de datas** (`_no_ano`/`_no_mes`/`_nos_anos` nos repositórios, `calendar.monthrange` para o último dia) — `extract()` no WHERE impede o índice; `extract` só como projeção (`label`/`group_by`) ou residual sobre conjunto não contíguo combinado com a faixa.
- **Pool de conexões** (`models/base.py::_engine_kwargs`): URLs `sqlite` usam `NullPool` + `check_same_thread=False` (SQLite não se beneficia de pooling; o `QueuePool` default esgotava com as threads de portal do TestClient/executor do agendador → hang de 30s + `TimeoutError` intermitente). PostgreSQL mantém o `QueuePool` default.
- `POST /init-db` — migra + seeds. `POST /recreate-db` — apaga tudo (`resetar_banco()`) + migra + seeds. ⚠️ **As duas exigem `APP_ENV=dev` + `confirmado=true`** (change `blindar-rotas-administrativas-banco`) e **não respondem a GET**: as duas chamam `seed_data()`, que faz DELETE FÍSICO em lançamento/qualificador/pagamento/órgão, e `SameSite=lax` manda o cookie de sessão em navegação top-level GET — um link de terceiro zerava a base do admin logado. A guarda de ambiente valia só para `recreate-db` porque a spec dizia isso; a assimetria vinha da spec, não do código, e deixava desprotegida a rota que ninguém achava perigosa. Guarda única em `_exigir_seed_destrutivo_autorizado`. Falha devolve mensagem genérica (`str(e)` do SQLAlchemy vaza SQL, tabela e coluna).
- `migrations/legacy/` são scripts históricos absorvidos (não executar).
- **Saldo é por fundo** (F2.4): a tabela legada `flc_saldo_conta` foi removida na migração `0006` (dados migrados para `flc_saldo_conta_fundo` sob o fundo `GERAL`). Relatórios leem o agregado via `SaldoContaRepository` (strangler sobre `vw_flc_saldo_conta_agregado`), sem mudar. A tela grava/edita/inativa no modelo novo (`saldo_conta_service` é fachada sobre `saldo_fundo_service`/`importar_lote`).
- **Views de banco** (`vw_flc_*`, ex.: saldo por fundo): vivem NAS MIGRAÇÕES (`op.execute("CREATE VIEW ...")`), nunca no `Base.metadata` (quebraria o anti-deriva). Evolução de view = nova revisão com DROP+CREATE. SQL das views deve ser portável SQLite/PostgreSQL (sem GROUP_CONCAT/STRING_AGG; concat com `||`, janela com LAG/OVER). Leitura via `repositories/saldo_fundo_repository.py` (bind params + Decimal).

## Arquitetura

### Camadas
```
web/ (rotas FastAPI)  →  services/ (lógica de negócio)  →  repositories/ (queries)  →  models/ (SQLAlchemy)
                                  ↑
                            domain/ (Pydantic DTOs: *Create, *Out, *Update)
```
- **`web/`**: Cada arquivo é um módulo de rotas (`base.py`, `relatorios.py`, `simulador_cenarios.py`, etc.). Todos compartilham um único `router` e `templates` Jinja2 expostos por `web/__init__.py`. As rotas são registradas por **import side-effect** na linha final de `web/__init__.py` — adicionar um novo módulo de rotas requer importá-lo lá.
- **`services/relatorio/`**: Pacote modular que substituiu o antigo `relatorio_service.py` monolítico. Cada relatório (DFC, indicadores, previsão de receita, etc.) tem seu próprio service.
- **`domain/`**: DTOs Pydantic v2. Nomes seguem `<Entidade>Create` / `<Entidade>Out` / `<Entidade>Update`.

### Padrões importantes

**SafeAPIRouter** (`web/safe_router.py`): subclasse de `APIRouter` que envolve automaticamente todo endpoint com `handle_exceptions`. Esse wrapper faz log de exceções não tratadas, executa `db.session.rollback()` e retorna 500. Não é necessário decorar manualmente — mas alguns endpoints existentes ainda têm `@handle_exceptions` redundante por histórico.

**Sessão SQLAlchemy** (`models/base.py`): `SessionLocal` é um `scoped_session` global compartilhado. ⚠️ **Ciclo de vida POR REQUEST** (change `sessao-sqlalchemy-por-request`, R13): `SessaoPorRequestMiddleware` (`sessao_request.py`, ASGI puro — nunca `BaseHTTPMiddleware`, ver nota do CSRF) faz `SessionLocal.remove()` em `finally` a cada requisição — antes, com todos os endpoints `async def` na thread do event loop, o processo compartilhava UMA Session nunca fechada e o identity map devolvia estado de requests anteriores (leitura obsoleta). Limitação que PERMANECE: o I/O de banco síncrono continua dentro de `async def` (bloqueia o event loop) — a solução real é endpoints `def` + injeção de sessão, mudança estrutural própria. `Base.query` está disponível como query property no estilo Flask-SQLAlchemy (`Lancamento.query.all()`). Há também `Query.get_or_404` monkey-patched que levanta `HTTPException(404)`. O helper `_DB` em `models/base.py` simula a interface mínima de Flask-SQLAlchemy (`db.session`, `db.create_all()`, `db.drop_all()`) — não é Flask, apesar do nome.

**Bootstrap** (`fluxocaixa/__init__.py:create_app`): A cada start o app executa `preparar_banco()` (migrações Alembic, controlado por `AUTO_MIGRATE`), `seed_dominio()` (dados de domínio: tipos/origens de lançamento e parâmetros globais — cria só o que falta, nunca altera existentes) e, se `SEED_DEMO_DATA` (default true), `seed_data()` (limpa e repopula os dados de exemplo — desativar em instalação com dados reais).

**Convenções de schema**:
- Todas as tabelas têm prefixo `flc_` (ex: `flc_lancamento`, `flc_qualificador`).
- PKs nomeadas `seq_*`, FKs `cod_*` ou `seq_*_fk`.
- Soft delete via `ind_status` (`'A'` ativo / `'I'` inativo) — preferir filtrar do que `DELETE`.
- Auditoria: `dat_inclusao`, `cod_pessoa_inclusao`, `dat_alteracao`, `cod_pessoa_alteracao`.
- Valores monetários: `NUMERIC(18,2)` — nunca `Float`.
- `flc_qualificador` é hierárquico (auto-FK em `cod_qualificador_pai`); folha = sem filhos ativos. Helper: `Qualificador.is_folha()`.

**Modelo de simulação de cenários** (F6.2 — `flc_simulador_cenario` + **`flc_cenario_config`**): a config vive numa tabela só, discriminada pela PERNA — `cod_tipo_lancamento` `'C'`/`'D'`, o MESMO código do lançamento, com FK para o domínio (a referência unifica assim, "reusando o código já existente em FLC_LANCAMENTO"; só ficou possível depois da F6.1b). Unicidade por (cenário, perna); ajustes em **`flc_cenario_ajuste`** com FK para a config. Substituiu QUATRO tabelas espelhadas — e o espelho vivia também no serviço: `executar_simulacao` tinha ~200 linhas duplicadas (as duas funções MANUAL diferiam em UMA linha funcional) e virou um despacho por `cod_tipo_modelo`. ⚠️ **Catálogo em código** (`CATALOGO_MODELOS` em `models/simulador_cenario.py`) declara a PERNA aplicável de cada modelo — MANUAL/FORMULA/CRESCIMENTO_ANO/MEDIA_CRESCIMENTO em ambas, econométricos só em crédito, LOA/MEDIA_HISTORICA só em débito. A validação **recupera** uma garantia que as tabelas separadas davam por construção; sem ela, LOA em receita passaria. ⚠️ **Sinal único (R6)**: `val_projetado` sempre positivo e o sinal na perna, ENTRADA e saída — a série que alimenta os modelos também vai em magnitude. Isso consertou um bug antigo: `projetar_media_historica` aplica `max(valor, 0)` e, com despesa chegando negativa, projetava ZERO para toda despesa. `flc_projecao_valor.cod_tipo` convergiu de `'R'` para `'C'` — não há mais duas representações de crédito. A rede `tests/caracterizacao_previsao.py` congela a série de entrada e a saída dos modelos determinísticos (o treino dos econométricos fica fora: depende de libs opcionais). ⚠️ Os guards de import de ML em `modelos_economicos_service` usam `except Exception`, não `ImportError`: XGBoost/LightGBM levantam erro próprio quando a lib está instalada e a `.dylib` não carrega (falta `libomp` no macOS) — com `ImportError` o módulo inteiro morria e levava junto os modelos sem relação com ML. ⚠️ **Backtest: zero é medição e agregação profunda** (change `backtest-metricas-e-hierarquia-profunda`, previsao R16): `obter_recomendacoes` testa `is not None` (viés 0.0 virava "sem dado" pela sentinela falsy); o backtest roda nas **FOLHAS** (`is_folha`, origem única) e `_obter_hierarquia_qualificadores` devolve **ancestral → folhas descendentes** (subida pela cadeia de pais, com guarda de ciclo) — o pai de nível 1 numa árvore de 3+ níveis agregava só os filhos diretos de nível 2 (sem lançamentos) e ficava vazio; a mesma folha aparece sob todos os ancestrais e o backtest deduplica antes de treinar. ⚠️ **Ajuste rateado por periodicidade** (change `ajuste-cenario-por-periodicidade`, previsao R15): o ajuste do cenário MANUAL é preenchido por MÊS; em quinzenal/semanal o valor mensal (V ou percentual) é **rateado pela quota de períodos do mês na série** (`Counter` sobre `serie_de_datas`) — antes o valor cheio era emitido em cada período e R$ 120 mil/mês viravam R$ 240–600 mil; MENSAL/ANUAL têm quota 1 (mecanismo único, inerte onde já estava certo — a golden MANUAL/MENSAL não se moveu). ⚠️ **Despacho no serviço e visualização por versão** (change `despacho-de-modelos-no-servico`, previsao R14): `modelos_economicos_service.calcular_projecao(tipo_modelo, ...)` concentra a tabela modelo → (janela, mínimo, motor) — a rota `/simulador/calcular-projecao` só faz parse+chamada+serialização (eram 160 linhas com o bloco histórico+mínimo repetido 6×); insuficiência e modelo desconhecido são `RegraNegocioError`. `GET /simulador/{id}` serve a **última versão PUBLICADA** (`projecao_versao_service.resultado_da_versao` reconstrói o shape de `executar_simulacao` a partir de `flc_projecao_valor`; aviso `data-testid="origem-versao"` na tela) — abrir a página NÃO treina modelos; sem versão publicada executa ao vivo (Executar continua a ação explícita; padrão F5.2). Parse de formulário deduplicado: `_parse_cenario_form` único para criar/atualizar (defaults simétricos) e `web/cenario_form.py::parse_config_base` servindo simulador (sufixo `_cenario`, JSON) e fórmulas (sem sufixo, dict). ⚠️ **Transação única na escrita** (change `transacao-unica-cenario-e-backtest`, previsao R13): `criar_simulador_cenario`/`atualizar_simulador_cenario` são DONOS da transação — repositório com `commit: bool = True` (create_simulador/config/ajuste, delete_ajustes/parametros), tudo `commit=False` + um commit final + rollback em exceção. Antes, falha na config deixava cenário órfão commitado, e o update commitava a exclusão dos ajustes antigos antes de os novos falharem. `salvar_recomendacoes` do backtest idem (DELETE+INSERTs atômicos — a sessão é global e um DELETE pendente seria efetivado pelo commit da próxima operação). ⚠️ Descoberta no mesmo change: `flc_backtest_recomendacao` NÃO existia em banco novo (SQL cru sem model/migração) e `db.text` nem existe no helper `_DB` — salvar/obter recomendações quebravam na primeira linha; entraram `models/backtest_recomendacao.py` + migração `0034` (sem `ind_status`: dado de máquina, regravado a cada backtest) e `text()` do SQLAlchemy. ⚠️ **Modelos corrigidos** (change `modelos-econometricos-corrigidos`, previsao R12): o deslocamento que torna a série positiva (HW `mul`/Box-Cox) é REVERTIDO após o forecast (antes inflava toda projeção em `1−min`, inclusive no fallback); datas por `_datas_do_ano_base` (relativedelta — `date(ano, i+1, 1)` estourava com 13+ períodos e quinzenal/semanal usam até 52); **fallback nunca silencioso** — a projeção carrega `attrs['degradacao']` e `executar_simulacao` devolve `degradacoes` no resultado (padrão `projecao_origem.ao_vivo`); fórmula com parâmetro faltante levanta `RegraNegocioError` citando a variável (antes projetava `base` em silêncio — a massa de caracterização registra valor 0 para as variáveis por isso); `validar_formula` é SÓ parse (avaliar com 1.0 recusava fórmula com singularidade); warnings confinados aos `fit()` via `_sem_avisos_de_convergencia` (o filterwarnings global suprimia warnings do processo inteiro); diagnóstico por `logging`, nunca `print` (guarda em `test_modelos_econometricos.py`). ⚠️ **Série histórica única** (change `serie-historica-unica-previsao`, previsao R11): TODA leitura de série histórica da previsão (bases de fórmula, `obter_dados_historicos*`, acumulados/perfil sazonal do crescimento, listagem de anos) filtra `ind_status='A'` — a mesma série do backtest, que sempre filtrou; usa `extract`, nunca `strftime` (só SQLite; o projeto suporta PostgreSQL); e NÃO engole exceção de banco (`except → {}/0.0` projetava zero com cara de dado apurado). Guarda estrutural em `src/tests/unit/test_serie_historica.py`; o perfil uniforme 1/12 continua SÓ para ano sem movimento. Snapshots completos são serializados em `flc_simulador_cenario_historico.json_snapshot`. Veja `services/simulador_cenario_service.py`, `services/previsao_service.py`, `services/modelos_economicos_service.py`, `services/feature_engineering.py`.

**Hierarquia sem ciclo e travessia terminante** (F6.7 — `cadastros-nucleo` R16–R18): reapontar um qualificador para si mesmo ou para um descendente é `RegraNegocioError`; reapontar+renomear nó com descendentes **renomeia a subárvore em cascata**, com confirmação. ⚠️ **O card previa `RecursionError`; a sonda mediu TRAVAMENTO.** `get_root` era `while node.pai: node = node.pai` — laço, não recursão: não levantava nada, prendia a thread. `tipo_fluxo` depende dele e aparece em ~47 pontos, e produção roda `gunicorn --workers 1`, então UMA requisição derrubava o app inteiro (pior que os 500 de `nivel`/`path_completo`, que ao menos terminam). Hoje `get_root`, `nivel`, `path_completo`, `get_todos_filhos` e `categoria_fiscal_service.categoria_resolvida` carregam conjunto de visitados. ⚠️ **A terminação vale INDEPENDENTE da guarda**: a guarda impede criar ciclo pelo serviço, não alcança dado legado, importação nem escrita direta no banco — defesa em profundidade aqui é o único recurso contra o que já existe. ⚠️ Em `categoria_resolvida` o `vistos` é **separado do memo**: o memo só é gravado depois do laço, então sem ele a subida não terminava e `caminho` crescia sem limite. ⚠️ A **auto-referência era recusada por ACIDENTE** do prefixo (`"7.1"` não começa com `"7.1."`); e a regra do prefixo valida só o nó editado, então renomear o nó para caber sob o próprio descendente passava e criava o ciclo. **Cascata (R17)**: o mapa `seq → código novo` é calculado e validado POR INTEIRO antes de gravar — unicidade contra o banco e entre os próprios códigos gerados —, porque aplicar em ordem e falhar no meio deixaria a árvore pela metade. Efeito colateral aceito: `services/loa_service.py::encontrar_qualificador` (era `web/loa.py`) casa por código ou descrição, então planilha com código antigo passa a casar só pela descrição. ⚠️ **O BDD dos ciclos roda sob `signal.alarm`**: sem teto de tempo, uma regressão que devolva o laço infinito **trava a suíte** em vez de falhar — e suíte travada não diz o que está errado (provado removendo a proteção: o teste acusou `TRAVOU` em 5s).

⚠️ **Teste que só cobre o caminho de ERRO de uma função não cobre a função.** A F6.5 deixou um `NameError` em `update_qualificador` (a assinatura não ganhou `cod_categoria_fiscal`, a atribuição sim — um `str.replace` casou a forma de `create_qualificador`, com o parâmetro no início da linha, e não a de `update_qualificador`). **Editar qualquer qualificador dava 500, e 566 pytest + 48 Playwright passaram verdes**: o único teste que chamava a função esperava `RegraNegocioError` levantada ANTES da linha quebrada. Mesma família do resíduo da F6.1b (substituição em lote que acerta uma forma e erra a outra). ⚠️ **`pyflakes` acha isso em segundos** — o projeto não tem linter configurado; `uv pip install --python .venv/bin/python pyflakes && .venv/bin/python -m pyflakes src/fluxocaixa/` (as 4 ocorrências de `pd` em anotações-string são falso positivo do import tardio).

**Qualificador por exercício e identidade estável** (F10.1–F10.5 — `cadastros-nucleo` R25–R30, `previsao` R17, migrações `0035`/`0036`): a classificação orçamentária pertence a um EXERCÍCIO — `flc_qualificador.num_ano_exercicio` NOT NULL (default Python = ano corrente), unicidade `(ano, código)` **entre ativos** (índice parcial `ux_flc_qualificador_ano_codigo_ativo`; a unique global caiu), pai e filho no mesmo exercício (nas duas portas). ⚠️ **SEM replicação da história** (decisão D1 do design da F10.1, desvio deliberado da concepção): até a leitura ser year-aware, espelhos duplicariam cada nó em toda tela de instalação migrada — e a suíte (banco novo) passaria verde mesmo assim; o plano existente virou o **plano base** e a imutabilidade começa no primeiro exercício aberto. Por isso a ordem foi F10.1 → F10.2 → F10.4 → F10.3 → F10.5. **Identidade estável**: `cod_rubrica_raiz` é o "CPF" da rubrica — nasce = próprio seq (evento ORM `after_insert`, vale para seeds/testes), é propagada pela cópia e NUNCA muda com renome/renumeração/reapontamento (`update_qualificador` não a expõe). **Série histórica por raiz** (F10.2): `services/serie_historica.py::seqs_da_rubrica` é a ORIGEM ÚNICA da costura — `formula_engine`, `modelos_economicos_service` e `backtest_service` consultam `seq_qualificador IN (...)`, nunca igualdade crua (guarda estrutural em `src/tests/unit/test_serie_por_raiz.py`); o resultado da simulação declara o treino (`series_info` por perna, bloco `data-testid="info-serie-treinada"`; < 12 pontos exibe a sugestão de prever no pai — F10.5). **Leitura por exercício** (F10.4): `resolver_exercicio_do_plano(ano)` (próprio → anterior mais recente → posterior mais antigo — registros de ano sem plano apontam para o base) é a origem única; listagens do repositório aceitam o recorte, DFC/comparativa/indicadores/LDO usam o plano resolvido do ano do relatório, combos de tela usam `exercicio_corrente()`, e a tela de qualificadores tem combo `data-testid="filtro-exercicio"` (criação herda o filtro; edição NÃO expõe o ano). **Abertura de exercício** (F10.3): `abrir_exercicio(origem, novo, confirmado=True)` — permissão `FC_ABRIR_EXERCICIO`, cópia atômica em DUAS passadas (linhas sem pai + remapeamento por mapa em memória — resiste a código que não deriva do pai), só ATIVOS, leva marcação PRÓPRIA de categoria (nunca a resolvida) e a raiz; LOA/dotação/programação nunca (estrutura, não saldo); destino com plano ativo é recusado (abertura ≠ sincronização); autor carimbado (`cod_pessoa_inclusao`, migração 0036). **Herança da raiz** (F10.5): desdobramento/fusão/reativação são UM gesto — select `herdar-raiz` na criação; validação: raiz existe e NÃO está em uso por ativo do mesmo exercício (série somada em dobro); herdar de inativa é a reativação. ⚠️ **Regra de transição da escrita** (D5): lançamento/importação/ajuste validam qualificador do exercício do registro **só quando existe plano ativo naquele ano** (`validar_qualificador_do_exercicio`) — instalação que nunca abriu exercício se comporta como sempre. BDDs usam ilhas 2070–2093; E2E: plano-ilha 2078 no seed (`telas_por_exercicio`/`abertura_exercicio`/`heranca_raiz`/`serie_treinada.spec.ts`).

**Movimento próprio de nó-pai no DFC** (F6.6 — `relatorios` R20): qualificador com filhos ativos **e** movimento próprio (lançamentos seus, ou projeção endereçada a ele) ganha uma **linha filha** com essa parcela, e o nó passa a ser a soma dos filhos. ⚠️ **Eram DOIS vazamentos**, não um: (1) `_recompor_pais` SUBSTITUÍA o pai pela soma dos filhos em todas as colunas, então o realizado próprio sumia nos **meses fechados** de um ano parcialmente aberto; (2) `_projetar_folhas` retorna cedo em nó com filhos, então a **projeção endereçada ao próprio nó** ficava no mapa sem ser lida — acontece quando uma folha vira pai DEPOIS de a versão ter sido publicada (a F6.4 permite, com confirmação), e o valor está numa versão publicada, que é registro histórico e não se reescreve. ⚠️ **Materializar, não somar**: `_recompor_pais` somar em vez de substituir **duplicaria os filhos**, porque `build_node` já entrega o pai com próprio + filhos. Materializando a parcela como filho em `build_node`, o invariante "pai é a soma dos filhos" vira **verdadeiro por construção** e `_recompor_pais` NÃO MUDA UMA LINHA — se precisar mudar, o desenho escorregou. E como a linha é **folha**, `_projetar_folhas` a alcança e lê a projeção do nó: um mecanismo, dois vazamentos. A linha só aparece com movimento próprio de fato — árvore bem formada (lançamentos só em folha) não vê diferença nenhuma, e é por isso que a golden `dfc_mes`/`dfc_ano` não se moveu. ⚠️ **Drill-down**: a linha leva o `seq` REAL do qualificador (precisa dele para saber de quem são os lançamentos), então sem o marcador `proprio` o recorte `[seq] + descendentes` devolveria a subárvore inteira — o oposto do que ela representa. O marcador viaja na query da célula (`data-proprio`), no espírito do `id=0` da linha sintética da R13. ⚠️ **O BDD usa o ANO CORRENTE com mês anterior, não ilha no passado**: `_recompor_pais` só roda sob `if meses_abertos:`, então num ano todo fechado o vazamento não se manifesta e o teste passaria por vacuidade — mesmo motivo pelo qual a F5.2 usa o ano corrente e pelo qual `dfc_projetado` fica fora da golden (`CAMPOS_EXCLUIDOS`, `_meses_abertos` usa `date.today()`).

**Metas fiscais por categoria explícita** (F6.5 — `relatorios` R17–R19, `cadastros-nucleo` R15): as metas da LDO deixam de casar substring na descrição do qualificador. ⚠️ **O defeito não era imprecisão, era cegueira à hierarquia**: a lista só tem folhas (`is_folha()`) e o casamento era na descrição da folha — um bloco "EDUCAÇÃO" casaria a palavra mas não é folha, e as folhas sob ele não casam, então a meta dava R$ 0,00 e exibia **"ATENÇÃO"**, indistinguível de descumprimento real. O relatório não separava *"aplicou pouco"* de *"não achei nada"*. **`flc_categoria_fiscal`** é domínio cadastrável (sigla, `cod_base_calculo` 'R' RCL / 'D' despesa total, `cod_sentido` 'P' piso / 'T' teto, `val_limite`, `val_limite_atencao`), seedado com PESSOAL/SAUDE/EDUCACAO — ⚠️ os valores do seed são **partida, não verdade**: o piso da saúde é 15% para município e **12% para estado**, e o limite de pessoal da LRF reparte por poder; por isso moram em tabela e o seed **nunca altera existente**. ⚠️ `cod_base_calculo` não é generalização gratuita: o serviço **já** usava denominadores diferentes (pessoal sobre RCL, saúde/educação sobre despesa total) — sem a coluna isso voltaria como `if sigla == 'PESSOAL'`, a heurística de novo. **A marcação HERDA pela árvore, mais próximo vence** (`categoria_fiscal_service.categoria_resolvida`, origem única como `is_folha`/`valor_com_sinal`/`periodo_resolver`): marca-se o BLOCO e as folhas herdam; marcação própria vence a do pai. Marcar folha a folha trocaria erro silencioso automático por erro silencioso manual — esquecer uma folha entre quarenta subnotifica um piso constitucional. ⚠️ **Marcar NÃO exige folha** — exceção deliberada aos R12–R14, porque marcar o bloco é o propósito. ⚠️ **A categoria resolvida NÃO é persistida**: é função da marcação + posição, e a F6.4 liberou o reapontamento de pai, que a muda para a subárvore inteira. A resolução **memoiza o caminho inteiro** (não só a ponta) por chamada de relatório — sem isso o laço faz N × profundidade de lazy loads. A tela mostra a categoria **e se é própria ou herdada**: herança sem visibilidade repetiria o defeito ("por que esta rubrica entrou no piso da saúde?" não pode ser pergunta que só o código responde). ⚠️ **Dois números fabricados, destinos opostos**: `divida_consolidada_rcl = 45.0` era exibido como "45.0% — DENTRO DA META" e foi **REMOVIDO** (não há fonte de estoque de dívida no sistema; parametrizar moveria a invenção para uma tela e lhe daria cara de dado apurado); `meta_superavit = loa × 0.02` virou `flc_meta_fiscal_ano` (a meta vem da LDO da entidade — o usuário a conhece). Sem meta informada o status é **`SEM META`**, com cor neutra na tela: não é alerta de descumprimento, é ausência de meta. ⚠️ A migração `0015` **não converte dado**: varrer descrições para marcar automaticamente importaria os acertos da heurística junto com os erros ("Material de consumo — saúde" no piso da saúde), e os erros passariam a ter aparência de decisão humana. A marcação nasce vazia; até marcar, as metas apuram zero — preferível a apurar errado com cara de certo.

**Folha dinâmica em qualquer nível** (F6.4 — `cadastros-nucleo` R12–R14): folha = nó **sem filhos ativos**, em qualquer profundidade, e a hierarquia suporta 6 níveis. ⚠️ **Isto já funcionava** — `is_folha()`, o guard de `lancamento_service`, o `build_node` do DFC e o template da árvore sempre foram recursivos, sem teto: a "amarração a nível fixo" que a seção 3.6 do plano manda remover **não existia**. O trabalho foi fechar as portas que a profundidade escancara. ⚠️ **Origem única**: `Qualificador.is_folha()` é a ÚNICA resposta para "isto é folha?". Havia TRÊS implementações — as duas do repositório (`get_receita/despesa_qualificadores_folha`) montavam o conjunto de pais **dentro do recorte por prefixo** do código, então um filho fora do prefixo (dado legado, ou resultado de reapontar o pai numa edição, que não revalida a subárvore) nunca marcava o pai: ele era listado como folha e recusado pela validação de lançamento. A terceira, em `web/relatorios.py` (backtest), varria uma lista local e **ignorava o `ind_status` do filho**, sumindo com nós cujo único filho estava inativo. Mesmo padrão da F6.1 (`valor_com_sinal`) e da F6.3 (`periodo_resolver`). O custo é o N+1 de `is_folha()`, já pago em `web/relatorios.py`/`base.py`/`loa.py`; um `NOT EXISTS` em SQL seria uma QUARTA definição. ⚠️ **Aviso ao transformar folha em pai** (`confirmado=true`, padrão do R4): dispara nas **DUAS** portas — criar filho sob a folha **e** reapontar um nó existente para ela; guardar só a primeira seria ilusão de guarda, o mesmo estado entra pela segunda. O gatilho são os **lançamentos do futuro pai**, não "ele é folha" — nó que já é pai não pergunta nada. O banner reenvia o mesmo POST com o cadastro pendente em hidden (query params `confirmar_pai`/`pend_*`), porque aqui o pendente é um cadastro inteiro, não só um `seq` como na exclusão. ⚠️ **O ajuste de cenário não validava folha**, embora o plano cite os três verbos: `lancamento_service` e `mapeamento_service` validavam, `_criar_ajustes` não — e a validação ficou **fora** do `try/except (ValueError, IndexError)` daquela função, senão a regra de negócio passaria a depender de qual exceção o parser resolve engolir. ⚠️ **`num_qualificador` era `String(20)` e não cabia 6 níveis** (`1.100.200.300.400.500` = 21 chars): **SQLite não impõe tamanho de VARCHAR** e gravava calado, PostgreSQL recusa — o bug passava em dev e só apareceria em produção (migração `0014` alarga para 60). Pelo mesmo motivo o BDD afere a **capacidade declarada da coluna**, não o round-trip do valor, que passa em SQLite mesmo com a coluna curta. **Não há validação de profundidade máxima**: *"até 6 níveis"* é capacidade a garantir, não teto a impor — criá-lo seria introduzir a amarração que o card pede para remover. **Limitações conhecidas, deliberadas** (o plano pede avisar, não impedir nem migrar): após o "sim", o lançamento continua num nó que virou pai, e o DFC mostra `próprio + filhos` no realizado (`build_node`) contra `só filhos` no projetado (`_recompor_pais`, F5.2) para essa célula; e `update_qualificador` **não tem guarda de ciclo** — apontar um nó para um descendente faz `nivel`/`path_completo`/`get_root`/`build_node` recursarem sem fim (`RecursionError`, violando o R1). Ambas com card próprio.

**Origem única de (ano, período)** (F6.3 — `services/periodo_resolver.py`): as quatro periodicidades passam a existir de verdade. Antes o Python não tinha nada disso — `if ANUAL: … else: <mensal>` —, então QUINZENAL e SEMANAL, **oferecidas na tela**, caíam no ramo mensal: quem pedia "Semanal, 52 semanas" recebia 52 MESES. Os quatro cálculos: ANUAL → `(ano, 1)`; MENSAL → `(ano, mês)`; QUINZENAL → `(mês−1)×2 + (dia≤15 ? 1 : 2)`, vira no dia **16**; SEMANAL → `date.isocalendar()`. ⚠️ **Três armadilhas de calendário, todas contra a intuição**: (1) o ano do SEMANAL é o **ano ISO**, não o civil — 29/12/2025 está na semana 1 de **2026** e 01/01/2021 na semana 53 de **2020**; (2) o mês de uma semana é o da sua **quinta-feira** (usar a segunda joga a semana da virada no mês errado); (3) a **semana 53 existe** em ano ISO longo — presumir 52 é o erro clássico, e pedir a 53 num ano de 52 é `RegraNegocioError`, não `ValueError` cru. ⚠️ **Python puro, nunca SQL** (D3): a referência usa `TO_CHAR(data,'IYYY'/'IW')`, que é Oracle, e **SQLite não tem semana ISO** (`%W` conta do domingo) — por isso a agregação do realizado desce só até o **dia** em SQL (`GROUP BY` na data, portável) e a dobra em períodos é Python. **`flc_projecao_valor.mes` foi REMOVIDO** (migração `0013`): o mês é função pura de (periodicidade, ano, período) e vem de `mes_do_periodo` na leitura — mesmo princípio do saldo agregado da F2.1, que também nunca é persistido. `ANUAL` devolve mês `None` de propósito: é a redistribuição por perfil histórico da F5.2 que o transforma em doze meses. ⚠️ **A migração do ANUAL não é cópia de coluna**: os 12 registros mensais (que eram a *distribuição* de um total anual) **colapsam** num período só, preservando o total do ano — a forma muda, o número não; o `downgrade` reexpande em 12 partes iguais e a distribuição original **não volta** (perda documentada). `flc_simulador_cenario.meses_projecao` → `num_periodos`: o campo sempre guardou períodos, e a tela já gravava semanas nele. O casamento do realizado (`projecao_versao_service`) usa o período resolvido da **data do lançamento** — é aqui que o resolver ganha função, não só existência: antes um cenário quinzenal recebia o realizado do mês inteiro na "quinzena" de mesmo número. Os rótulos `Q1…Qn`/`S1…Sn` da tela agora **viram o ano** (não existe `Q25`; a semana vira em 52 **ou** 53 conforme o ano ISO). ⚠️ `projecao_versao_service` importa o **módulo** `simulador_cenario_service`, não o nome `executar_simulacao`: com `from … import <nome>` um stub de teste aplicado antes do primeiro import ficava grudado para o resto da suíte, e a ordem de coleta virava resultado de teste. Cobertura: BDD `previsao/periodo_resolver.feature` (as datas de virada são reais) + varreduras dia-a-dia em `unit/test_periodo_resolver.py` (anos 2020/2021/2024/2026 — a margem de ±7 dias na varredura é obrigatória, senão a semana da virada é vista pela metade).

**Fonte de recursos** (F9.1 — `flc_fonte_recurso` + FK em `flc_fundo`): catálogo padrão STN **decomposto** (`cod_identificador_exercicio` 1/2/9 + `cod_fonte_stn` 3 dígitos + `cod_detalhamento` local) e **versionado** por `num_exercicio_vigencia` — a tabela oficial muda por exercício; unicidade composta ENTRE ATIVOS validada no serviço (constraint de banco impediria conviver com inativas). ⚠️ `ind_vinculada` ('L'/'V') é **explícita, nunca derivada do código** (5xx-livre tem exceções). **Princípio: errar para baixo** — fonte desconhecida em carga nasce vinculada+pendente (`obter_ou_criar_pendente`, padrão do auto-cadastro de fundos); fundo sem fonte = pendente = **fora do grupo livre**. A view `vw_flc_saldo_fundo_fonte` (migração `0017`) entrega o saldo **BRUTO** por grupo ('L'/'V'/'P', `num_ordem_recente=1` = linha mais recente por conta/fundo); reservas/bloqueios (F7.4 futura) NÃO são embutidos — a subtração é única, na leitura da disponibilidade operacional (`saldo_bruto_por_grupo` em `saldo_fundo_repository`). Toda tela rotula **"operacional"** (≠ disponibilidade fiscal do RGF). A ponte fundo→fonte pressupõe fundo **mono-fonte** (hipótese registrada no change; multi-fonte não recebe FK). Telas: `/fontes-recurso` (catálogo + decomposição, `FC_CONS/FC_MANT/FC_IMP_FONTE_RECURSO`) e classificação na tela de fundos (`classificar_fundo`). Importação da tabela STN por adapter F2.5 (`fontes_recurso`). **Fonte no lançamento** (F9.2): `flc_lancamento.seq_fonte_recurso` FK **nullable** (migração `0018`; legado fica nulo — não se inventa fonte retroativamente); o processamento F4.3 estampa via `resolver_fonte_de_atributos` (chaves `fonte_recurso`→`cod_fonte`→`fonte` do `json_atributos`; valor ausente/não parseável → **sem fonte, nunca erro de linha** — fonte é dimensão opcional; import tardio dentro de `_gravar_lancamento`); porta manual tem select **sem default** (pré-marcar seria classificação silenciosa) e a tela de lançamentos filtra/exibe por fonte. ⚠️ Teste unitário que importe `fluxocaixa` NO TOPO do módulo quebra o isolamento de banco da suíte inteira (o engine nasce antes de o conftest forçar `DATABASE_URL` — 44 falhas de ordem); imports de app em `src/tests/unit/` são sempre tardios, dentro do teste. ⚠️ BDDs de fonte usam **vigências-ilha** (F9.1: 2031/2034/2037; F9.2: 2035) — cenário novo escolhe vigência não usada, senão o assert de "vigência vazia" de outro módulo quebra.

**Liberações do desembolso** (F7.1a — `flc_liberacao` + `flc_liberacao_evento` + `flc_pagamento_liberacao`, migração `0019`): a cota financeira que o Tesouro solta para o órgão pagar. ⚠️ **Liberação não movimenta caixa** — movimenta o saldo de CONTROLE. Três invariantes: (1) **livro de eventos** — criação/confirmação/cancelamento são linhas imutáveis em `flc_liberacao_evento`, gravadas NA MESMA transação do `cod_situacao` (R rascunho/C confirmada/X cancelada; confirmada nunca volta a rascunho; cancelar confirmada exige `confirmado=true` e é vetado com apropriações); (2) **pendente sempre derivado** — `saldo_liberado_pendente` (origem única em `liberacao_service`) = Σ confirmadas − Σ apropriações + Σ estornos; NÃO existe coluna `val_utilizado`; a apropriação é linha-evento (`cod_tipo_evento` 'A'/'E') em `flc_pagamento_liberacao`, que nasceu na F7.1a mas só ganha UI na F7.1b; (3) **fonte obrigatória sem default** + `cod_natureza_obrigacao` (D/O/J/F/V — não-D = "não gerenciável", entra na curva-base da simulação F7.2, não no veredicto). Validações: qualificador folha ativa DE DESPESA (`tipo_fluxo`), valor positivo. `flc_orgao` ganhou `ind_status`+auditoria (server_default espelhado no model — anti-deriva) e tela própria; órgão segue dimensão SÓ do desembolso. Permissões: `FC_CONS/MANT/CONF_LIBERACAO` (confirmar é ato distinto — OPERADOR mantém mas não confirma), `FC_CONS/MANT_ORGAO`. Telas `/liberacoes` (visão semanal seg–sex por natureza→órgão) e `/orgaos`. ⚠️ E2E roda com `SEED_DEMO_DATA=false`: massa de órgão/qualificador-despesa vive em `seed_usuarios_e2e.py`. BDDs do desembolso usam ilha 2038.

**Apropriação pagamento↔liberação** (F7.1b — migração `0020`): `flc_pagamento` alinhado (status, auditoria, `cod_origem` M/A, `seq_fonte_recurso`). ⚠️ **Qualificador é exigido pelo SERVIÇO em escrita nova, mas a coluna segue nullable** — backfill fabricaria classificação com cara de decisão humana; legado nulo fica visível como "sem apropriação" (sem qualificador não há candidata). Regras em `pagamento_service`: candidatas = liberações confirmadas do mesmo órgão/qualificador/fonte com saldo, mais antiga primeiro (`candidatas_para`); **estouro proibido nos dois sentidos** (cada apropriação ≤ saldo restante da liberação — pendente nunca negativo — e Σ ≤ valor do pagamento; alterar valor abaixo do apropriado é recusado); **fonte do pagamento é HERDADA da apropriação** (monofonte: primeira estampa, divergente é recusada, estornar tudo limpa — nunca editada direto); estorno é linha-evento 'E' (`estornar_apropriacao`), edição não existe; excluir é soft com `confirmado=true`, vetado com apropriações. Permissões novas: `FC_ALT/DEL/APROPRIAR_PAGAMENTO`.

**Repartição por fonte** (F9.3 — `flc_qualificador_fonte`, migração `0021`): percentuais-FALLBACK que repartem a projeção de receita por grupo de disponibilidade. Três invariantes em `reparticao_fonte_service`: (1) **conjunto atômico** — `definir_reparticao` valida soma = 100 e substitui o conjunto inteiro numa transação (linha avulsa exporia soma ≠ 100 a leitores); (2) qualificador **sem repartição vai ao grupo 'N'** (não classificado) em `repartir_valor` — NUNCA ao livre (erro para cima) nem erro (bloquearia a simulação); a F7.2 exclui o 'N' do veredicto autorizativo; (3) `sugestao_do_historico` calcula percentuais observados nos lançamentos estampados (F9.2) — **sugestão de tela, gravar é decisão humana**. Vigência anual como o catálogo. Só receita (despesa entra se a F7.2 provar necessidade). Tela `/reparticao-fonte` (pendências destacadas), permissões `FC_CONS/MANT_REPARTICAO_FONTE`.

**Simulação de disponibilidade** (F7.2 — `simulacao_desembolso_service`, migração `0022`): o para-brisa do desembolso. Curva MENSAL por grupo de fonte: `saldo bruto do grupo − reservas (F7.4, hoje 0 — a subtração ÚNICA é aqui) + receitas repartidas (F9.3) − despesas ajustadas − pendente posicionado − lote (rascunhos posicionados)`. ⚠️ Invariantes: (1) **modo prudente é o único autorizativo** — receita do grupo 'N' (sem repartição) fica FORA da curva; informativo inclui mas NUNCA confirma; (2) anti-dupla contagem por (qualificador × mês × grupo) com piso zero — pendente maior que a projeção não gera crédito; (3) pendente/lote posicionados pela `dat_prevista_desembolso` com **clamp**: anterior ao horizonte → primeiro mês (vencido desconta integral), posterior → fora; (4) **veredicto** OK/ALERTA/BLOQUEIO sobre o mínimo da curva COM lote × colchão do grupo (`flc_parametro_desembolso`, override por grupo vence o global; seed = 0.00); **insuficiência estrutural** (base SEM lote viola) é alerta à parte — "não é o lote"; (5) `confirmar_lote` é transação ÚNICA: snapshot imutável (`flc_simulacao_desembolso`) + rascunhos→confirmadas com eventos referenciando `SIM-{seq}` — nunca usar o `confirmar_liberacao` unitário em lote (commita por chamada). Fonte da projeção: `resolver_projecao` do DFC (publicada → ao vivo com aviso). Tela `/simulacao-desembolso` (`FC_EXEC_SIMULACAO_DESEMBOLSO`; confirmar exige `FC_CONF_LIBERACAO`; colchão `FC_MANT_PARAM_DESEMBOLSO`). ⚠️ BDD de veredicto usa grupo 'V' com saldo próprio — o 'L' recebe vazamento de rascunhos de outras features pelo clamp.

**Conferência e transferências** (F7.1c + F7.5 — migrações `0023`/`0024`): `flc_conferencia` foi RECONSTRUÍDA — o grão continua o dia, mas só sobrevivem os **apurados externos** (`val_apurado_liberacoes/pagamentos`); todas as colunas deriváveis sumiram (o legado era cópia de imagem de demo, descartado). **Previsto LOA, reservas e bloqueios** (F7.3a + F7.4 — migração `0025`): o previsto do desembolso é SEMPRE derivado (`previsto_loa_service`: LOA despesa × perfil do realizado do ano−1 com fallback 1/12; semanal por dias úteis; **previsto por órgão não existe** — a LOA é qualificador+ano, nunca ratear). **Teto do autorizado** em `confirmar_liberacao(confirmado=)`: exceder a LOA recusa sem `confirmado=true` citando o excedente; com ele confirma e o evento registra — alerta consciente, nunca bloqueio (UI: dois botões — confirmar / confirmar-excedendo); o lote (F7.2) não trava, os excedentes vão ao snapshot. **Reservas/bloqueios** (`flc_reserva_financeira` + `flc_reserva_evento`): valor corrente SEMPRE derivado (Σ constituição+reforços−reduções−liberações); administrativa acima do disponível exige `confirmado=true`, **judicial nunca pede confirmação** (não é escolha — só alerta) e liberar judicial exige a referência da ordem; `reservas_vigentes_do_grupo(grupo, hoje)` é a parcela da SUBTRAÇÃO ÚNICA na simulação (a fórmula da F7.2 deixou de ter zero). **Programação de desembolso** (F7.3b — `flc_programacao_desembolso`, migração `0026`): as cotas do decreto de programação financeira (LRF art. 8º), importáveis por planilha (`mes;orgao;valor;ato`, adapter F2.5 com o ano fixado pela rota). **Execução orçamentária E/L/P** (F8.2 — `flc_execucao_orcamentaria` + `flc_execucao_evento`, migração `0028`): o "provável" e o "devido" do funil. **Credenciais e força bruta** (change `endurecer-credenciais-e-antibruteforce`, spec `controle-acesso` R14 + R1/R4/R5 — `auth/service.py`, migração `0031`): bloqueio após `LOGIN_MAX_FALHAS` (5) falhas por `LOGIN_BLOQUEIO_SEGUNDOS` (15 min). ⚠️ **Durante o bloqueio a senha CORRETA também é recusada** — é o que torna o bloqueio útil; se ela passasse, ele só atrasaria o ataque pelo tempo de contar até cinco (é por isso que o cenário BDD manda a senha certa na sexta tentativa). ⚠️ **Mensagem sempre igual**, inclusive no bloqueio: dizer "conta bloqueada" devolveria a enumeração de usuários pela porta da frente; o bloqueio vai para o log do servidor, para o administrador conseguir explicar. ⚠️ **Tempo constante**: login inexistente compara contra `_HASH_DESCARTAVEL` — retornar cedo sem executar bcrypt (que custa ~100 ms de propósito) tornava a resposta medivelmente mais rápida e vazava a existência da conta mesmo com mensagem idêntica. ⚠️ **MODO DEMO desliga o bloqueio**: todos os visitantes compartilham a MESMA conta, então cinco erros de digitação — ou alguém agindo de propósito — trancariam a instância inteira; o mecanismo que protege uma conta viraria o próprio ataque. ⚠️ **Senha inicial do admin é ALEATÓRIA** quando `ADMIN_INITIAL_PASSWORD` não está definida, logada uma vez no boot (fechava a janela em que quem monitorava o deploy logava com `admin`/`admin` e tomava a conta) — **exceto em modo demo**, onde continua `SENHA_DEMO_ADMIN='admin'`, porque a tela de login EXIBE a credencial e uma senha aleatória tornaria o banner mentiroso e a demo inacessível. **Proteção CSRF** (change `protecao-csrf-global`, spec `controle-acesso` R12 — `auth/csrf.py`): token por SESSÃO (não por requisição — o sistema é usado com várias abas, e rotação faria a aba antiga falhar ao submeter, ensinando o usuário a recarregar tudo antes de agir). **Automação de lançamentos — motor de regras** (F4.2 — `src/fluxocaixa/services/regra/`): traduz regra em pt-BR → predicado sobre a staging da F4.1. **Automação de lançamentos — telas do motor** (F4.2b — `web/mapeamentos.py`, `web/termos_regra.py`, templates `mapeamentos.html`/`mapeamento_form.html`/`termos_regra.html`): CRUD de mapeamento (cabeçalho + itens num único form) e do dicionário de termos. **O texto é a verdade**: `txt_regra` é sempre texto pt-BR; o *builder* de linhas (`termo | operador | valor` + conectivo) é só açúcar de UI que **gera** texto, e o *modo avançado* (textarea) aceita a gramática inteira (`não`, parênteses, aninhamento). **Automação de lançamentos — processamento** (F4.3 — `services/processamento_service.py`): fecha o circuito, linha PENDENTE da staging → `flc_lancamento` com origem `Automático`. ⚠️ **Sem bookmark, sem janela, sem cold start**: o recorte é `ind_status_processamento='0'` (índice `ix_flc_etl_staging_fonte_status`) — a linha pendente **é** o marco, e é exato. A referência varre por janela de data porque lá o status é só escape de resync; portar isso seria copiar um acidente (e o card do plano pede `MAX(dat_lancamento)`, a data contábil, que **retroage** — a própria referência usa o carimbo de escrita, monotônico, por isso). **Âncora**: `flc_lancamento.seq_etl_staging` (FK nullable — manual/importado não vêm da staging) dá idempotência, rastro até o `json_atributos` cru e o resync **cirúrgico de verdade** (a referência, sem ela, reseta o ano inteiro do item sujo). **Laço** por mapeamento ativo (recorte = sistema de origem + ano, mesmo join do preview; `val_referencia <> 0`): linha casa com 1 item → lançamento; com **2+ → ERRO explícito** na linha citando os qualificadores (classificação dá UM destino; a referência gera N lançamentos e duplica o valor no caixa); com 0 → segue pendente (outro mapeamento pode ser o dono). **Tipo e sinal**: tipo do `ind_tipo` do mapeamento (1→"Entrada", 2→"Saída") e origem `Automático`, ambos resolvidos **por descrição** via `services/dominio_lancamento.py` (os FKs são autoincremento — "Entrada=1" é incidental no seed); `val_lancamento = val_referencia` × -1 se `ind_inversao_sinal='1'`, **igual para receita e despesa** (na referência a inversão é silenciosamente ignorada na despesa). O sinal **não é reimposto pelo tipo** — já vem assinado do `CASE` contábil da query da fonte; forçar dupla-negaria. **Sujo** := item **sem** `dat_ultima_execucao` — `alterar_mapeamento` o descarta quando o conteúdo muda. ⚠️ NÃO comparar `dat_alteracao > dat_ultima_execucao` (como a referência, que usa `DTH_*`): aqui as colunas são `Date`, então editar e processar **no mesmo dia** nunca acusaria sujeira. Item sujo também **reabre as linhas em ERRO** do mapeamento (o erro é do conjunto de regras, não da linha; e linha em erro não é candidata, logo o resync por FK não a alcança). **Disparo**: automático ao fim de `executar_fonte` de fonte `LANCAMENTO` — **depois** do commit e **fora** do try da extração, para que falha de classificação não reclassifique a carga — processando por sistema de origem (`processar_sistema_origem`); mais a ação manual da tela. **Log**: `flc_execucao_mapeamento` (grão = mapeamento; o resync não tem execução de extração onde se pendurar), com gerados/erros/removidos e status derivado como na extração. **Tela** `/mapeamentos/execucoes` (`web/processamento.py`): `FC_CONS_EXECUCAO_MAPEAMENTO` consulta, `FC_EXEC_MAPEAMENTO` processa (gera lançamentos — não é consulta). ⚠️ **O resync APAGA** o lançamento automático em vez de inativar, divergindo da convenção de soft-delete do projeto: é linha de máquina, integralmente reproduzível a partir da staging (que fica), o rastro vive na FK + no log, e inativar acumularia uma geração de lixo a cada resync que todo relatório (DFC, KPIs) teria de filtrar para sempre — um passo em falso e o valor dobra. Só toca lançamento de origem `Automático` **com** `seq_etl_staging`; manual/importado nunca. O bug do plano "receita e despesa na mesma tabela nas duas pontas" é **impossível** aqui: só existe `flc_lancamento`. ⚠️ **O processamento é UMA transação** (change `processamento-idempotente-resync-cirurgico`): lançamentos + resync + status das linhas + marco `dat_ultima_execucao` comitam juntos — comitar os lançamentos antes de marcar as linhas abria a janela em que queda do processo (deploy, OOM) deixava linhas PENDENTES com lançamentos já gravados, e o próximo processamento **duplicava o caixa**; por isso `marcar_ok_lote`/`marcar_erro_lote` ganharam `commit: bool = True` (o processamento passa `False` e só faz flush) e é também por isso que zerar os contadores no `except` é VERDADE (o rollback desfaz tudo). Defesa em profundidade: `_linhas_candidatas` exclui linha que já tem lançamento ativo referenciando-a (`NOT EXISTS`) — duplicar passa a exigir dois erros independentes. ⚠️ **O escopo do resync é o do MAPEAMENTO dono do item**: qualificador + `num_ano_exercicio` + `seq_sistema_origem`, via join `Lancamento → EtlStaging → FonteExtracao`. O recorte antigo (qualificador + origem) parecia cirúrgico e não era: o mesmo qualificador-folha é destino de itens em mapeamentos de exercícios diferentes no uso normal (um mapeamento por ano), e o resync de um item de 2026 apagava os lançamentos de 2024/2025 — que aquele mapeamento não é capaz de regerar (perda permanente se os outros estiverem inativos). **Sinal contábil** (`valor = débito − crédito` se o 1º dígito da conta contábil ∈ {1,3,5,7}, senão `crédito − débito`): **não é código** — vai na `query` da fonte `BANCO_SQL`, mapeada para `val_saldo`, e a staging já nasce com o valor assinado (o motor de regras nunca vê débito/crédito).
