# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão Geral

Sistema web de fluxo de caixa para prefeituras, estados e órgãos públicos. Backend em **FastAPI + SQLAlchemy 2.0**, templates **Jinja2** server-rendered (não é SPA), banco padrão **SQLite** em `instance/fluxo.db` (PostgreSQL suportado via `DATABASE_URL`). Inclui motor de simulação de cenários (regressão, média histórica, modelos econométricos com XGBoost/LightGBM/statsmodels) para projeção de receitas e despesas públicas.

## Comandos Essenciais

### Banco de dados
- **Schema gerenciado por Alembic** (`alembic/` na raiz). Toda mudança de schema = revisão com upgrade/downgrade: `alembic revision --autogenerate -m "descricao"` após alterar models. Nunca use `create_all` para tabelas de negócio.
- Boot (`create_app`): `preparar_banco()` (`bootstrap_db.py`) roda `alembic upgrade head` se `AUTO_MIGRATE` (default true); depois `seed_dominio()` (sempre, idempotente e não destrutivo) e `seed_data()` se `SEED_DEMO_DATA` (default true).
- **Banco legado** (criado antes do Alembic, sem `alembic_version`): boot aborta pedindo `alembic stamp 0001` (marca a baseline; o boot aplica as migrações posteriores). NUNCA `stamp head` na adoção — marcaria migrações não executadas como aplicadas.
- Teste anti-deriva: `src/tests/integration/test_migracoes.py::test_sem_deriva_entre_models_e_migracoes` falha se um model mudar sem migração correspondente.
- Naming convention de constraints em `models/base.py` (`NAMING_CONVENTION`) — obrigatória para o batch mode do SQLite; não criar constraints com nomes fora do padrão.
- **Pool de conexões** (`models/base.py::_engine_kwargs`): URLs `sqlite` usam `NullPool` + `check_same_thread=False` (SQLite não se beneficia de pooling; o `QueuePool` default esgotava com as threads de portal do TestClient/executor do agendador → hang de 30s + `TimeoutError` intermitente). PostgreSQL mantém o `QueuePool` default.
- `GET /init-db` — migra + seeds. `GET /recreate-db` — apaga tudo (`resetar_banco()`) + migra + seeds.
- `migrations/legacy/` são scripts históricos absorvidos (não executar).
- **Saldo é por fundo** (F2.4): a tabela legada `flc_saldo_conta` foi removida na migração `0006` (dados migrados para `flc_saldo_conta_fundo` sob o fundo `GERAL`). Relatórios leem o agregado via `SaldoContaRepository` (strangler sobre `vw_flc_saldo_conta_agregado`), sem mudar. A tela grava/edita/inativa no modelo novo (`saldo_conta_service` é fachada sobre `saldo_fundo_service`/`importar_lote`).
- **Views de banco** (`vw_flc_*`, ex.: saldo por fundo): vivem NAS MIGRAÇÕES (`op.execute("CREATE VIEW ...")`), nunca no `Base.metadata` (quebraria o anti-deriva). Evolução de view = nova revisão com DROP+CREATE. SQL das views deve ser portável SQLite/PostgreSQL (sem GROUP_CONCAT/STRING_AGG; concat com `||`, janela com LAG/OVER). Leitura via `repositories/saldo_fundo_repository.py` (bind params + Decimal).

## Arquitetura

### Camadas
```
web/ (rotas FastAPI)  →  services/ (lógica de negócio)  →  repositories/ (queries)  →  models/ (SQLAlchemy)
                                  ↑
                            domain/ (Pydantic DTOs: *Create, *Out, *Update)
```
- **`web/`**: Cada arquivo é um módulo de rotas (`base.py`, `relatorios.py`, `simulador_cenarios.py`, etc.). Todos compartilham um único `router` e `templates` Jinja2 expostos por `web/__init__.py`. As rotas são registradas por **import side-effect** na linha final de `web/__init__.py` — adicionar um novo módulo de rotas requer importá-lo lá.
- **`services/relatorio/`**: Pacote modular que substituiu o antigo `relatorio_service.py` monolítico. Cada relatório (DFC, indicadores, previsão de receita, etc.) tem seu próprio service.
- **`domain/`**: DTOs Pydantic v2. Nomes seguem `<Entidade>Create` / `<Entidade>Out` / `<Entidade>Update`.

### Padrões importantes

**SafeAPIRouter** (`web/safe_router.py`): subclasse de `APIRouter` que envolve automaticamente todo endpoint com `handle_exceptions`. Esse wrapper faz log de exceções não tratadas, executa `db.session.rollback()` e retorna 500. Não é necessário decorar manualmente — mas alguns endpoints existentes ainda têm `@handle_exceptions` redundante por histórico.

**Sessão SQLAlchemy** (`models/base.py`): `SessionLocal` é um `scoped_session` global compartilhado. `Base.query` está disponível como query property no estilo Flask-SQLAlchemy (`Lancamento.query.all()`). Há também `Query.get_or_404` monkey-patched que levanta `HTTPException(404)`. O helper `_DB` em `models/base.py` simula a interface mínima de Flask-SQLAlchemy (`db.session`, `db.create_all()`, `db.drop_all()`) — não é Flask, apesar do nome.

**Bootstrap** (`fluxocaixa/__init__.py:create_app`): A cada start o app executa `preparar_banco()` (migrações Alembic, controlado por `AUTO_MIGRATE`), `seed_dominio()` (dados de domínio: tipos/origens de lançamento e parâmetros globais — cria só o que falta, nunca altera existentes) e, se `SEED_DEMO_DATA` (default true), `seed_data()` (limpa e repopula os dados de exemplo — desativar em instalação com dados reais).

**Convenções de schema**:
- Todas as tabelas têm prefixo `flc_` (ex: `flc_lancamento`, `flc_qualificador`).
- PKs nomeadas `seq_*`, FKs `cod_*` ou `seq_*_fk`.
- Soft delete via `ind_status` (`'A'` ativo / `'I'` inativo) — preferir filtrar do que `DELETE`.
- Auditoria: `dat_inclusao`, `cod_pessoa_inclusao`, `dat_alteracao`, `cod_pessoa_alteracao`.
- Valores monetários: `NUMERIC(18,2)` — nunca `Float`.
- `flc_qualificador` é hierárquico (auto-FK em `cod_qualificador_pai`); folha = sem filhos ativos. Helper: `Qualificador.is_folha()`.

**Modelo de simulação de cenários** (F6.2 — `flc_simulador_cenario` + **`flc_cenario_config`**): a config vive numa tabela só, discriminada pela PERNA — `cod_tipo_lancamento` `'C'`/`'D'`, o MESMO código do lançamento, com FK para o domínio (a referência unifica assim, "reusando o código já existente em FLC_LANCAMENTO"; só ficou possível depois da F6.1b). Unicidade por (cenário, perna); ajustes em **`flc_cenario_ajuste`** com FK para a config. Substituiu QUATRO tabelas espelhadas — e o espelho vivia também no serviço: `executar_simulacao` tinha ~200 linhas duplicadas (as duas funções MANUAL diferiam em UMA linha funcional) e virou um despacho por `cod_tipo_modelo`. ⚠️ **Catálogo em código** (`CATALOGO_MODELOS` em `models/simulador_cenario.py`) declara a PERNA aplicável de cada modelo — MANUAL/FORMULA/CRESCIMENTO_ANO/MEDIA_CRESCIMENTO em ambas, econométricos só em crédito, LOA/MEDIA_HISTORICA só em débito. A validação **recupera** uma garantia que as tabelas separadas davam por construção; sem ela, LOA em receita passaria. ⚠️ **Sinal único (R6)**: `val_projetado` sempre positivo e o sinal na perna, ENTRADA e saída — a série que alimenta os modelos também vai em magnitude. Isso consertou um bug antigo: `projetar_media_historica` aplica `max(valor, 0)` e, com despesa chegando negativa, projetava ZERO para toda despesa. `flc_projecao_valor.cod_tipo` convergiu de `'R'` para `'C'` — não há mais duas representações de crédito. A rede `tests/caracterizacao_previsao.py` congela a série de entrada e a saída dos modelos determinísticos (o treino dos econométricos fica fora: depende de libs opcionais). ⚠️ Os guards de import de ML em `modelos_economicos_service` usam `except Exception`, não `ImportError`: XGBoost/LightGBM levantam erro próprio quando a lib está instalada e a `.dylib` não carrega (falta `libomp` no macOS) — com `ImportError` o módulo inteiro morria e levava junto os modelos sem relação com ML. Snapshots completos são serializados em `flc_simulador_cenario_historico.json_snapshot`. Veja `services/simulador_cenario_service.py`, `services/previsao_service.py`, `services/modelos_economicos_service.py`, `services/feature_engineering.py`.

**Hierarquia sem ciclo e travessia terminante** (F6.7 — `cadastros-nucleo` R16–R18): reapontar um qualificador para si mesmo ou para um descendente é `RegraNegocioError`; reapontar+renomear nó com descendentes **renomeia a subárvore em cascata**, com confirmação. ⚠️ **O card previa `RecursionError`; a sonda mediu TRAVAMENTO.** `get_root` era `while node.pai: node = node.pai` — laço, não recursão: não levantava nada, prendia a thread. `tipo_fluxo` depende dele e aparece em ~47 pontos, e produção roda `gunicorn --workers 1`, então UMA requisição derrubava o app inteiro (pior que os 500 de `nivel`/`path_completo`, que ao menos terminam). Hoje `get_root`, `nivel`, `path_completo`, `get_todos_filhos` e `categoria_fiscal_service.categoria_resolvida` carregam conjunto de visitados. ⚠️ **A terminação vale INDEPENDENTE da guarda**: a guarda impede criar ciclo pelo serviço, não alcança dado legado, importação nem escrita direta no banco — defesa em profundidade aqui é o único recurso contra o que já existe. ⚠️ Em `categoria_resolvida` o `vistos` é **separado do memo**: o memo só é gravado depois do laço, então sem ele a subida não terminava e `caminho` crescia sem limite. ⚠️ A **auto-referência era recusada por ACIDENTE** do prefixo (`"7.1"` não começa com `"7.1."`); e a regra do prefixo valida só o nó editado, então renomear o nó para caber sob o próprio descendente passava e criava o ciclo. **Cascata (R17)**: o mapa `seq → código novo` é calculado e validado POR INTEIRO antes de gravar — unicidade contra o banco e entre os próprios códigos gerados —, porque aplicar em ordem e falhar no meio deixaria a árvore pela metade. Efeito colateral aceito: `web/loa.py::_encontrar_qualificador` casa por código ou descrição, então planilha com código antigo passa a casar só pela descrição. ⚠️ **O BDD dos ciclos roda sob `signal.alarm`**: sem teto de tempo, uma regressão que devolva o laço infinito **trava a suíte** em vez de falhar — e suíte travada não diz o que está errado (provado removendo a proteção: o teste acusou `TRAVOU` em 5s).

⚠️ **Teste que só cobre o caminho de ERRO de uma função não cobre a função.** A F6.5 deixou um `NameError` em `update_qualificador` (a assinatura não ganhou `cod_categoria_fiscal`, a atribuição sim — um `str.replace` casou a forma de `create_qualificador`, com o parâmetro no início da linha, e não a de `update_qualificador`). **Editar qualquer qualificador dava 500, e 566 pytest + 48 Playwright passaram verdes**: o único teste que chamava a função esperava `RegraNegocioError` levantada ANTES da linha quebrada. Mesma família do resíduo da F6.1b (substituição em lote que acerta uma forma e erra a outra). ⚠️ **`pyflakes` acha isso em segundos** — o projeto não tem linter configurado; `uv pip install --python .venv/bin/python pyflakes && .venv/bin/python -m pyflakes src/fluxocaixa/` (as 4 ocorrências de `pd` em anotações-string são falso positivo do import tardio).

**Movimento próprio de nó-pai no DFC** (F6.6 — `relatorios` R20): qualificador com filhos ativos **e** movimento próprio (lançamentos seus, ou projeção endereçada a ele) ganha uma **linha filha** com essa parcela, e o nó passa a ser a soma dos filhos. ⚠️ **Eram DOIS vazamentos**, não um: (1) `_recompor_pais` SUBSTITUÍA o pai pela soma dos filhos em todas as colunas, então o realizado próprio sumia nos **meses fechados** de um ano parcialmente aberto; (2) `_projetar_folhas` retorna cedo em nó com filhos, então a **projeção endereçada ao próprio nó** ficava no mapa sem ser lida — acontece quando uma folha vira pai DEPOIS de a versão ter sido publicada (a F6.4 permite, com confirmação), e o valor está numa versão publicada, que é registro histórico e não se reescreve. ⚠️ **Materializar, não somar**: `_recompor_pais` somar em vez de substituir **duplicaria os filhos**, porque `build_node` já entrega o pai com próprio + filhos. Materializando a parcela como filho em `build_node`, o invariante "pai é a soma dos filhos" vira **verdadeiro por construção** e `_recompor_pais` NÃO MUDA UMA LINHA — se precisar mudar, o desenho escorregou. E como a linha é **folha**, `_projetar_folhas` a alcança e lê a projeção do nó: um mecanismo, dois vazamentos. A linha só aparece com movimento próprio de fato — árvore bem formada (lançamentos só em folha) não vê diferença nenhuma, e é por isso que a golden `dfc_mes`/`dfc_ano` não se moveu. ⚠️ **Drill-down**: a linha leva o `seq` REAL do qualificador (precisa dele para saber de quem são os lançamentos), então sem o marcador `proprio` o recorte `[seq] + descendentes` devolveria a subárvore inteira — o oposto do que ela representa. O marcador viaja na query da célula (`data-proprio`), no espírito do `id=0` da linha sintética da R13. ⚠️ **O BDD usa o ANO CORRENTE com mês anterior, não ilha no passado**: `_recompor_pais` só roda sob `if meses_abertos:`, então num ano todo fechado o vazamento não se manifesta e o teste passaria por vacuidade — mesmo motivo pelo qual a F5.2 usa o ano corrente e pelo qual `dfc_projetado` fica fora da golden (`CAMPOS_EXCLUIDOS`, `_meses_abertos` usa `date.today()`).

**Metas fiscais por categoria explícita** (F6.5 — `relatorios` R17–R19, `cadastros-nucleo` R15): as metas da LDO deixam de casar substring na descrição do qualificador. ⚠️ **O defeito não era imprecisão, era cegueira à hierarquia**: a lista só tem folhas (`is_folha()`) e o casamento era na descrição da folha — um bloco "EDUCAÇÃO" casaria a palavra mas não é folha, e as folhas sob ele não casam, então a meta dava R$ 0,00 e exibia **"ATENÇÃO"**, indistinguível de descumprimento real. O relatório não separava *"aplicou pouco"* de *"não achei nada"*. **`flc_categoria_fiscal`** é domínio cadastrável (sigla, `cod_base_calculo` 'R' RCL / 'D' despesa total, `cod_sentido` 'P' piso / 'T' teto, `val_limite`, `val_limite_atencao`), seedado com PESSOAL/SAUDE/EDUCACAO — ⚠️ os valores do seed são **partida, não verdade**: o piso da saúde é 15% para município e **12% para estado**, e o limite de pessoal da LRF reparte por poder; por isso moram em tabela e o seed **nunca altera existente**. ⚠️ `cod_base_calculo` não é generalização gratuita: o serviço **já** usava denominadores diferentes (pessoal sobre RCL, saúde/educação sobre despesa total) — sem a coluna isso voltaria como `if sigla == 'PESSOAL'`, a heurística de novo. **A marcação HERDA pela árvore, mais próximo vence** (`categoria_fiscal_service.categoria_resolvida`, origem única como `is_folha`/`valor_com_sinal`/`periodo_resolver`): marca-se o BLOCO e as folhas herdam; marcação própria vence a do pai. Marcar folha a folha trocaria erro silencioso automático por erro silencioso manual — esquecer uma folha entre quarenta subnotifica um piso constitucional. ⚠️ **Marcar NÃO exige folha** — exceção deliberada aos R12–R14, porque marcar o bloco é o propósito. ⚠️ **A categoria resolvida NÃO é persistida**: é função da marcação + posição, e a F6.4 liberou o reapontamento de pai, que a muda para a subárvore inteira. A resolução **memoiza o caminho inteiro** (não só a ponta) por chamada de relatório — sem isso o laço faz N × profundidade de lazy loads. A tela mostra a categoria **e se é própria ou herdada**: herança sem visibilidade repetiria o defeito ("por que esta rubrica entrou no piso da saúde?" não pode ser pergunta que só o código responde). ⚠️ **Dois números fabricados, destinos opostos**: `divida_consolidada_rcl = 45.0` era exibido como "45.0% — DENTRO DA META" e foi **REMOVIDO** (não há fonte de estoque de dívida no sistema; parametrizar moveria a invenção para uma tela e lhe daria cara de dado apurado); `meta_superavit = loa × 0.02` virou `flc_meta_fiscal_ano` (a meta vem da LDO da entidade — o usuário a conhece). Sem meta informada o status é **`SEM META`**, com cor neutra na tela: não é alerta de descumprimento, é ausência de meta. ⚠️ A migração `0015` **não converte dado**: varrer descrições para marcar automaticamente importaria os acertos da heurística junto com os erros ("Material de consumo — saúde" no piso da saúde), e os erros passariam a ter aparência de decisão humana. A marcação nasce vazia; até marcar, as metas apuram zero — preferível a apurar errado com cara de certo.

**Folha dinâmica em qualquer nível** (F6.4 — `cadastros-nucleo` R12–R14): folha = nó **sem filhos ativos**, em qualquer profundidade, e a hierarquia suporta 6 níveis. ⚠️ **Isto já funcionava** — `is_folha()`, o guard de `lancamento_service`, o `build_node` do DFC e o template da árvore sempre foram recursivos, sem teto: a "amarração a nível fixo" que a seção 3.6 do plano manda remover **não existia**. O trabalho foi fechar as portas que a profundidade escancara. ⚠️ **Origem única**: `Qualificador.is_folha()` é a ÚNICA resposta para "isto é folha?". Havia TRÊS implementações — as duas do repositório (`get_receita/despesa_qualificadores_folha`) montavam o conjunto de pais **dentro do recorte por prefixo** do código, então um filho fora do prefixo (dado legado, ou resultado de reapontar o pai numa edição, que não revalida a subárvore) nunca marcava o pai: ele era listado como folha e recusado pela validação de lançamento. A terceira, em `web/relatorios.py` (backtest), varria uma lista local e **ignorava o `ind_status` do filho**, sumindo com nós cujo único filho estava inativo. Mesmo padrão da F6.1 (`valor_com_sinal`) e da F6.3 (`periodo_resolver`). O custo é o N+1 de `is_folha()`, já pago em `web/relatorios.py`/`base.py`/`loa.py`; um `NOT EXISTS` em SQL seria uma QUARTA definição. ⚠️ **Aviso ao transformar folha em pai** (`confirmado=true`, padrão do R4): dispara nas **DUAS** portas — criar filho sob a folha **e** reapontar um nó existente para ela; guardar só a primeira seria ilusão de guarda, o mesmo estado entra pela segunda. O gatilho são os **lançamentos do futuro pai**, não "ele é folha" — nó que já é pai não pergunta nada. O banner reenvia o mesmo POST com o cadastro pendente em hidden (query params `confirmar_pai`/`pend_*`), porque aqui o pendente é um cadastro inteiro, não só um `seq` como na exclusão. ⚠️ **O ajuste de cenário não validava folha**, embora o plano cite os três verbos: `lancamento_service` e `mapeamento_service` validavam, `_criar_ajustes` não — e a validação ficou **fora** do `try/except (ValueError, IndexError)` daquela função, senão a regra de negócio passaria a depender de qual exceção o parser resolve engolir. ⚠️ **`num_qualificador` era `String(20)` e não cabia 6 níveis** (`1.100.200.300.400.500` = 21 chars): **SQLite não impõe tamanho de VARCHAR** e gravava calado, PostgreSQL recusa — o bug passava em dev e só apareceria em produção (migração `0014` alarga para 60). Pelo mesmo motivo o BDD afere a **capacidade declarada da coluna**, não o round-trip do valor, que passa em SQLite mesmo com a coluna curta. **Não há validação de profundidade máxima**: *"até 6 níveis"* é capacidade a garantir, não teto a impor — criá-lo seria introduzir a amarração que o card pede para remover. **Limitações conhecidas, deliberadas** (o plano pede avisar, não impedir nem migrar): após o "sim", o lançamento continua num nó que virou pai, e o DFC mostra `próprio + filhos` no realizado (`build_node`) contra `só filhos` no projetado (`_recompor_pais`, F5.2) para essa célula; e `update_qualificador` **não tem guarda de ciclo** — apontar um nó para um descendente faz `nivel`/`path_completo`/`get_root`/`build_node` recursarem sem fim (`RecursionError`, violando o R1). Ambas com card próprio.

**Origem única de (ano, período)** (F6.3 — `services/periodo_resolver.py`): as quatro periodicidades passam a existir de verdade. Antes o Python não tinha nada disso — `if ANUAL: … else: <mensal>` —, então QUINZENAL e SEMANAL, **oferecidas na tela**, caíam no ramo mensal: quem pedia "Semanal, 52 semanas" recebia 52 MESES. Os quatro cálculos: ANUAL → `(ano, 1)`; MENSAL → `(ano, mês)`; QUINZENAL → `(mês−1)×2 + (dia≤15 ? 1 : 2)`, vira no dia **16**; SEMANAL → `date.isocalendar()`. ⚠️ **Três armadilhas de calendário, todas contra a intuição**: (1) o ano do SEMANAL é o **ano ISO**, não o civil — 29/12/2025 está na semana 1 de **2026** e 01/01/2021 na semana 53 de **2020**; (2) o mês de uma semana é o da sua **quinta-feira** (usar a segunda joga a semana da virada no mês errado); (3) a **semana 53 existe** em ano ISO longo — presumir 52 é o erro clássico, e pedir a 53 num ano de 52 é `RegraNegocioError`, não `ValueError` cru. ⚠️ **Python puro, nunca SQL** (D3): a referência usa `TO_CHAR(data,'IYYY'/'IW')`, que é Oracle, e **SQLite não tem semana ISO** (`%W` conta do domingo) — por isso a agregação do realizado desce só até o **dia** em SQL (`GROUP BY` na data, portável) e a dobra em períodos é Python. **`flc_projecao_valor.mes` foi REMOVIDO** (migração `0013`): o mês é função pura de (periodicidade, ano, período) e vem de `mes_do_periodo` na leitura — mesmo princípio do saldo agregado da F2.1, que também nunca é persistido. `ANUAL` devolve mês `None` de propósito: é a redistribuição por perfil histórico da F5.2 que o transforma em doze meses. ⚠️ **A migração do ANUAL não é cópia de coluna**: os 12 registros mensais (que eram a *distribuição* de um total anual) **colapsam** num período só, preservando o total do ano — a forma muda, o número não; o `downgrade` reexpande em 12 partes iguais e a distribuição original **não volta** (perda documentada). `flc_simulador_cenario.meses_projecao` → `num_periodos`: o campo sempre guardou períodos, e a tela já gravava semanas nele. O casamento do realizado (`projecao_versao_service`) usa o período resolvido da **data do lançamento** — é aqui que o resolver ganha função, não só existência: antes um cenário quinzenal recebia o realizado do mês inteiro na "quinzena" de mesmo número. Os rótulos `Q1…Qn`/`S1…Sn` da tela agora **viram o ano** (não existe `Q25`; a semana vira em 52 **ou** 53 conforme o ano ISO). ⚠️ `projecao_versao_service` importa o **módulo** `simulador_cenario_service`, não o nome `executar_simulacao`: com `from … import <nome>` um stub de teste aplicado antes do primeiro import ficava grudado para o resto da suíte, e a ordem de coleta virava resultado de teste. Cobertura: BDD `previsao/periodo_resolver.feature` (as datas de virada são reais) + varreduras dia-a-dia em `unit/test_periodo_resolver.py` (anos 2020/2021/2024/2026 — a margem de ±7 dias na varredura é obrigatória, senão a semana da virada é vista pela metade).

**Automação de lançamentos — staging genérica** (F4.1 — destino `LANCAMENTO`): uma fonte pode ter `cod_destino=LANCAMENTO` (além de `SALDO_FUNDO`). `executar_fonte` roteia por `fonte.cod_destino`: `SALDO_FUNDO`→`importar_lote` (intacto); `LANCAMENTO`→`services/staging_service.py::gravar_lote`, que deposita as linhas CRUAS em `flc_etl_staging` (`models/etl_staging.py`) para classificação na F4.2. A execução (`flc_execucao_extracao`) é criada e recebe `flush` ANTES da carga, pois `flc_etl_staging.seq_execucao_extracao` é FK. O contrato do conector ganhou `LinhaExtraida.json_atributos` (`extracao/conector.py`) e o layout de mapeamento ganhou `capturar_atributos` (`LayoutApiRest`) — quando ligado, `mapear_item` despeja a linha de origem em `json_atributos` (não afeta o caminho de saldo). Uma fonte `LANCAMENTO` deve mapear `dat_saldo`/`val_saldo` **e** ligar `capturar_atributos` (`_validar_layout_lancamento`, no criar/alterar). `flc_etl_staging` é área de trabalho recarregável: **sem** `ind_status` (soft-delete); tem `ind_status_processamento` (`0` pendente/`1` ok/`2` erro) + `dsc_erro` (truncado em 500 ANTES de gravar). `staging_service`: `gravar_lote`/`marcar_ok`/`marcar_erro`/`reprocessar_execucao` (reset por `seq_execucao_extracao` — resync da F4.3). Staging vazia→`SEM_DADOS` com mensagem (carga não silenciosa). NÃO nesta fase: tradutor de regras, `flc_lancamento`, sinal contábil, bookmark (F4.2/F4.3).

**Automação de lançamentos — motor de regras** (F4.2 — `src/fluxocaixa/services/regra/`): traduz regra em pt-BR → predicado sobre a staging da F4.1. Pipeline: `substituicao.py` (termos ATIVOS do cadastro, fronteira de palavra, **mais longo vence** — sem isso "Unidade Gestora" comeria o prefixo de "Unidade Gestora Emitente"; o casamento roda no lexer, não num `re.sub` cego, que corromperia termo dentro de literal) → `parser.py` (descida recursiva dep-free, gramática FECHADA: `=` `<>` `começa com` `>` `<` `>=` `<=` `em (…)` · `e` `ou` `não` · parênteses · literais) → `ast.py` (o **contrato**) → `renderer.py` (**único ponto que fala com o banco**). Fachada: `traduzir_regra(txt)` → expressão, `validar_regra(txt)` → `(ok, erro)`, `preview_regra(txt, seq_sistema_origem, num_ano_exercicio=None, limite)` → `{total, amostra}` (roda o predicado contra `flc_etl_staging`, sem gravar nem mudar status; o recorte é o do mapeamento — sistema de origem + ano —, não a fonte). ⚠️ **NUNCA construir texto SQL** — o renderer só devolve objetos de expressão SQLAlchemy; é isso que torna a injeção impossível por construção (na implementação de referência o `txt_regra` é SQL cru concatenado em INSERT/UPDATE/DELETE, sem validação). Trecho não reconhecido = erro de parse explícito, nunca *fallthrough* pro banco. **Dicionário cadastrável** (`flc_termo_regra`, `termo_regra_service`): termo → campo, com `cod_origem_campo` `COLUNA` (restrito à whitelist `COLUNAS_PERMITIDAS` em `models/termo_regra.py` — regra de negócio não alcança coluna de controle da staging) ou `ATRIBUTO` (chave livre de `json_atributos`, parametrizada); `cod_tipo` (TEXTO/NUMERO/DATA) valida operador↔tipo. Portabilidade: `json_atributos[k].as_string()` compila p/ `json_extract` (SQLite) e `->>` (PostgreSQL). **Modelo** (migração `0009`): `flc_mapeamento` virou cabeçalho (ano, `ind_tipo` 1=Rec/2=Desp, `seq_sistema_origem` FK, descrição) + `flc_item_mapeamento` (qualificador **folha**, `txt_regra`, `ind_inversao_sinal`, `dat_ultima_execucao`). Unicidade **(ano, tipo, sistema_origem)** entre ativos, validada no serviço (a referência usa (ano,tipo) e deixa a origem fora da chave — bloquearia uma 2ª origem). `mapeamento_service` exige ao menos 1 item ativo, qualificador folha e não repetido entre ativos. `ind_inversao_sinal` aqui é só cadastro — aplicação, bookmark, gravação em `flc_lancamento` e resync são F4.3. As **telas** vivem na F4.2b (abaixo).

**Automação de lançamentos — telas do motor** (F4.2b — `web/mapeamentos.py`, `web/termos_regra.py`, templates `mapeamentos.html`/`mapeamento_form.html`/`termos_regra.html`): CRUD de mapeamento (cabeçalho + itens num único form) e do dicionário de termos. **O texto é a verdade**: `txt_regra` é sempre texto pt-BR; o *builder* de linhas (`termo | operador | valor` + conectivo) é só açúcar de UI que **gera** texto, e o *modo avançado* (textarea) aceita a gramática inteira (`não`, parênteses, aninhamento). Quem decide builder × avançado ao editar é o **servidor**, com o próprio parser (`services/regra/builder.py::regra_para_builder`): representável = comparação única ou cadeia de UM conectivo só entre comparações; o estado vai pro template como JSON em `<script id="regras-estado">`. Itens repetíveis viajam num hidden `itens_raw` com JSON (padrão `json_layout_raw` da extração) — **cada linha carrega `seq_item_mapeamento`**, e é essa PK que preserva o marco de execução no serviço. Endpoints JSON (`fetch`+`FormData`, lê `d.detail` no erro 400): `POST /mapeamentos/validar-regra` e `POST /mapeamentos/preview-regra` — exigem só `FC_CONS_MAPEAMENTO`, pois **não gravam**. Permissões novas: `FC_CONS_TERMO_REGRA`/`FC_MANT_TERMO_REGRA` (estilo das telas de extração: um MANT cobre incluir/alterar/inativar); mapeamento reusa as 4 `FC_*_MAPEAMENTO`. ⚠️ **Identidade dos itens** (`alterar_mapeamento`): item com PK é atualizado NO LUGAR e `dat_alteracao` só é carimbado se o conteúdo mudou de fato; item **inalterado preserva** `dat_ultima_execucao`, item **alterado o descarta** (não foi executado na forma em que está — é a AUSÊNCIA do marco que a F4.3 lê como sujo); item sem PK entra; item ausente do POST é **inativado**, não apagado. NUNCA recriar os itens: `dat_ultima_execucao` é o marco que a F4.3 usa para detectar item sujo (`dat_alteracao > dat_ultima_execucao`), e recriá-los faria todo save marcar tudo como sujo — a "limpeza cirúrgica" viraria recarga total do ano. ⚠️ **Limitação conhecida**: a gramática não define escape de aspas simples (o literal é lido com `find("'")`), então **valor com apóstrofo é recusado** pelo builder com mensagem de negócio (`services/regra/builder.py::_literal`); os campos classificados são códigos (natureza, UG, fonte), onde isso não é caso real. E2E: `seed_usuarios_e2e.py` semeia termos, sistema `SIS_E2E`, fonte LANCAMENTO e linhas de staging fictícias; como a unicidade é (ano, tipo, sistema origem), **cada teste do spec usa o seu ano**.

**Automação de lançamentos — processamento** (F4.3 — `services/processamento_service.py`): fecha o circuito, linha PENDENTE da staging → `flc_lancamento` com origem `Automático`. ⚠️ **Sem bookmark, sem janela, sem cold start**: o recorte é `ind_status_processamento='0'` (índice `ix_flc_etl_staging_fonte_status`) — a linha pendente **é** o marco, e é exato. A referência varre por janela de data porque lá o status é só escape de resync; portar isso seria copiar um acidente (e o card do plano pede `MAX(dat_lancamento)`, a data contábil, que **retroage** — a própria referência usa o carimbo de escrita, monotônico, por isso). **Âncora**: `flc_lancamento.seq_etl_staging` (FK nullable — manual/importado não vêm da staging) dá idempotência, rastro até o `json_atributos` cru e o resync **cirúrgico de verdade** (a referência, sem ela, reseta o ano inteiro do item sujo). **Laço** por mapeamento ativo (recorte = sistema de origem + ano, mesmo join do preview; `val_referencia <> 0`): linha casa com 1 item → lançamento; com **2+ → ERRO explícito** na linha citando os qualificadores (classificação dá UM destino; a referência gera N lançamentos e duplica o valor no caixa); com 0 → segue pendente (outro mapeamento pode ser o dono). **Tipo e sinal**: tipo do `ind_tipo` do mapeamento (1→"Entrada", 2→"Saída") e origem `Automático`, ambos resolvidos **por descrição** via `services/dominio_lancamento.py` (os FKs são autoincremento — "Entrada=1" é incidental no seed); `val_lancamento = val_referencia` × -1 se `ind_inversao_sinal='1'`, **igual para receita e despesa** (na referência a inversão é silenciosamente ignorada na despesa). O sinal **não é reimposto pelo tipo** — já vem assinado do `CASE` contábil da query da fonte; forçar dupla-negaria. **Sujo** := item **sem** `dat_ultima_execucao` — `alterar_mapeamento` o descarta quando o conteúdo muda. ⚠️ NÃO comparar `dat_alteracao > dat_ultima_execucao` (como a referência, que usa `DTH_*`): aqui as colunas são `Date`, então editar e processar **no mesmo dia** nunca acusaria sujeira. Item sujo também **reabre as linhas em ERRO** do mapeamento (o erro é do conjunto de regras, não da linha; e linha em erro não é candidata, logo o resync por FK não a alcança). **Disparo**: automático ao fim de `executar_fonte` de fonte `LANCAMENTO` — **depois** do commit e **fora** do try da extração, para que falha de classificação não reclassifique a carga — processando por sistema de origem (`processar_sistema_origem`); mais a ação manual da tela. **Log**: `flc_execucao_mapeamento` (grão = mapeamento; o resync não tem execução de extração onde se pendurar), com gerados/erros/removidos e status derivado como na extração. **Tela** `/mapeamentos/execucoes` (`web/processamento.py`): `FC_CONS_EXECUCAO_MAPEAMENTO` consulta, `FC_EXEC_MAPEAMENTO` processa (gera lançamentos — não é consulta). ⚠️ **O resync APAGA** o lançamento automático em vez de inativar, divergindo da convenção de soft-delete do projeto: é linha de máquina, integralmente reproduzível a partir da staging (que fica), o rastro vive na FK + no log, e inativar acumularia uma geração de lixo a cada resync que todo relatório (DFC, KPIs) teria de filtrar para sempre — um passo em falso e o valor dobra. Só toca lançamento de origem `Automático` **com** `seq_etl_staging`; manual/importado nunca. O bug do plano "receita e despesa na mesma tabela nas duas pontas" é **impossível** aqui: só existe `flc_lancamento`.

**Sinal contábil** (`valor = débito − crédito` se o 1º dígito da conta contábil ∈ {1,3,5,7}, senão `crédito − débito`): **não é código** — vai na `query` da fonte `BANCO_SQL`, mapeada para `val_saldo`, e a staging já nasce com o valor assinado (o motor de regras nunca vê débito/crédito). É como a referência faz (na SQL de extração), só que sem duplicar a expressão em vários arquivos. Exemplo fictício:
```sql
SELECT dat_emissao AS data,
       CASE WHEN SUBSTR(cod_conta_contabil,1,1) IN ('1','3','5','7')
            THEN val_debito - val_credito ELSE val_credito - val_debito END AS valor,
       cod_natureza AS natureza, cod_ug AS ug
  FROM fato_lancamento WHERE dat_emissao BETWEEN :data_inicio AND :data_fim
```

**Tipo de lançamento `'C'`/`'D'` e a costura do sinal** (F6.1a+F6.1b): `cod_tipo_lancamento` é `CHAR(1)` — `'C'` crédito/receita, `'D'` débito/despesa — e **`val_lancamento` é SEMPRE POSITIVO**; o sinal do fluxo de caixa vem do tipo, pela costura `Lancamento.valor_com_sinal` (`hybrid_property`, forma Python + SQL). ⚠️ **Origem única do sinal**: toda agregação, comparação de sinal e derivação passa pela costura; `val_lancamento` cru só em **gravação** e **exibição de UMA linha**. Uma **guarda estrutural** (`src/tests/costura.py` + `test_costura_valor_com_sinal.py`, no espírito do `test_completude_permissoes`) varre `repositories/`, `services/relatorio/` e os agregadores de previsão (`formula_engine`, `modelos_economicos_service`, `backtest_service`, `projecao_versao_service`, `previsao_service`, `simulador_cenario_service` — lista `ARQUIVOS` em `costura.py`) e derruba a suíte se a coluna for lida crua fora da allow-list. ⚠️ **Os agregadores de previsão só entraram na varredura em 22/07/2026**: a F6.1b os deixou de fora e quatro leituras de INSTÂNCIA (`lanc.val_lancamento`) sobreviveram à migração — a substituição em lote casava `Lancamento.val_lancamento`, o atributo da **classe** —, invertendo em silêncio o sinal da série histórica de despesa que alimenta MEDIA_HISTORICA e o backtest. Ao migrar leituras, procure as DUAS formas. `get_sum_by_account_on_date_positive`/`_negative` testam `valor_com_sinal > 0`/`< 0`, o que é equivalente a `tipo == 'C'`/`'D'` por construção. A tabela de domínio e a FK foram **preservadas** (a referência dropou a tabela) e as descrições continuam **"Entrada"/"Saída"** — convergiu o código, não o vocabulário: `resolver_tipo("Entrada")` devolve `'C'`. Constantes `TIPO_CREDITO`/`TIPO_DEBITO` em `models/lancamento.py` (não em `dominio_lancamento`, para o model não depender de serviço).

⚠️ **A regra do sinal, nas três portas**: (1) **migração 0011** e (2) **automação F4.3** derivam o tipo do **SINAL** (`val = abs(valor)`, `tipo = 'C' se valor >= 0 senão 'D'`) — na automação a inversão do item é aplicada ANTES da derivação, então um estorno vira `'D'` sob o qualificador de receita (reversão de crédito é débito) e `ind_tipo` do mapeamento deixou de ditar o tipo; (3) **entrada manual/CSV** REJEITA valor não positivo com mensagem de negócio (o usuário escolhe o tipo no combo — derivar do sinal sobrescreveria a escolha em silêncio). A importação aceita `"Entrada"`/`"Saída"` e `'C'`/`'D'`; o código numérico `1`/`2` **não** é mais aceito. ⚠️ Derivar do sinal preserva o valor com sinal de QUALQUER linha, inclusive as incoerentes que o modelo antigo permitia (nada validava além de `!= 0`) — mas **os relatórios que separam receita de despesa POR TIPO redistribuem essas linhas entre as colunas**; o resultado líquido e as agregações por qualificador não se movem. A auditoria `services/auditoria_sinal_service.py` (só leitura) vigia o invariante: valor negativo sob `'C'` = `RECEITA_NEGATIVA`, sob `'D'` = `DESPESA_POSITIVA`.


**Rede de caracterização** (F6.1a — `src/tests/caracterizacao.py` + `test_caracterizacao_lancamento.py` + golden em `src/tests/fixtures/caracterizacao/`): congela os números de 11 relatórios derivados de lançamento (DFC mês/ano realizado, KPIs, saldos diários nos 2 modos, resumo, indicadores, controle de despesa, LDO, previsão×realizado, comparativa) para provar a F6.1b inerte. Regerar deliberadamente com `REGERAR_GOLDEN=1`. Três armadilhas resolvidas, todas necessárias para a golden não oscilar: (1) **ilha de datas 2019, ANTES do seed demo** — o seed gera saldos até `date.today()` e os relatórios de saldo carregam o último saldo anterior, então uma ilha posterior herdaria carry-forward que muda de um dia para o outro; (2) **chaves surrogate removidas** (`seq_*`, `*_id`, `id`) — mudam com a ordem de inserção de toda a suíte; (3) **recorte à ilha** dos 3 relatórios que varrem a árvore global de qualificadores (DFC `dre_data`, comparativa `data`, LDO `comparativo`), que trazem os qualificadores de outras features. ⚠️ A massa é DELIBERADAMENTE COERENTE: linha incoerente muda de tipo na migração por construção, e aí os relatórios que separam por tipo redistribuem — a golden prometeria "nada mudou" com asterisco. A semântica das incoerentes é fixada pelo BDD `tipo_lancamento_cd.feature`. ⚠️ Não tente podar por "sem movimento" olhando os números: código de qualificador `"1.90"` é indistinguível de R$ 1,90, e vários serviços (KPIs) já devolvem valor como string formatada — etiquetar na canonicalização não resolve. **DFC — estratégia Projetado** (F5.2 — `services/relatorio/dfc_service.py` + `dfc_projecao.py`): estratégia `realizado|projetado` + cenário no DFC. ## Dados sensíveis (repositório PÚBLICO — regras obrigatórias)

Em QUALQUER arquivo versionado (código, teste, doc, spec, exemplo de README):

- **NUNCA**: credenciais, tokens, hashes de senha, chaves reais; números de conta/agência verdadeiros, códigos de fundo em uso, valores financeiros reais; hosts e siglas de sistemas internos da organização de origem, IPs, caminhos de rede; dumps ou fixtures copiados de ambientes reais.
- **Bancos SQLite não são versionados** (`instance/*.db` no `.gitignore`): o `flc_usuario` guarda hash bcrypt da senha do admin e o banco pode conter dados digitados em dev. O Render cria o banco no boot (migrações + seeds).
- **Exemplos e testes**: identificadores claramente fictícios (agência `0001`, conta `12345-6`, fundo `9999`, valores `1234.56`). Nomes públicos de instituições financeiras e códigos de banco (001/104) são ok como referência; siglas de sistemas usados pela organização de origem e números reais de conta/valores, não.
- **Ao portar de uma implementação de referência**: trazer a regra de negócio, nunca o dado dos exemplos — substituir por fictícios. Não citar a organização de origem, nomes de repositórios internos nem caminhos de projetos não públicos.
- Antes de commitar, varrer o diff: `git diff --cached | grep -iE "senha|password|secret|token" `.
